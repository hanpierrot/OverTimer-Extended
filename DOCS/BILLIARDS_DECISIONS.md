## Implementation notes for the decisions

- **Profit-only tax.** `ITRSService.HandleMoneyChanged` adds *every* positive money delta to `earnedSinceLastBill`, regardless of reason. Plan: on a win, pay out in two `MoneyService.Add` calls — the stake back with reason `"billiards stake"` (exempt) and the profit with reason `"billiards"` (taxed) — and make `ITRSService` skip the exempt reason. `RunStatsService` counts positive deltas as "money earned" too; skip the same reason there. Stake = what the player actually paid (`bet × CostModifier(Billiards)`), so an Interest-style card makes the table worse, as the plan intends.
- **Forfeit rule.** `BilliardsApp.OnAppClosed`: state Aiming → keep round exactly as is; state Rolling/Judging → drop the round, bet lost; Racked → keep the racked table; Won/Lost → clear.

## Phase 2 notes (2026-10-14)

- **Pocket radii changed (physics constants):** corner `0.09 -> 0.15`, side `0.075 -> 0.12` (ball radius 0.0714 unchanged). Reason: with the plan's placeholder values the jaw points bounce a ball back out of a corner pocket before it counts as dropped, even on a straight-in shot (`straight_test` potted at no power at all with 0.09). A sweep of approach angles showed corner >= 0.14 drops every angle 10-80 deg and side >= 0.12 drops every angle 20-160 deg. `GameConfig.ValidateBilliards()` now also rejects corner < 1.9 x ball radius and side < 1.4 x ball radius, so art-derived radii (Q1) can't silently undo this. **Any later change to the radii needs a verifier run.**
- **Ball-ball step repeats (max 4 passes per tick, stops early) and a position-only cleanup after the cushion step (max 3 passes).** Not in the plan's step list. Reason: the plan's own S5 limit (no pair overlapping by more than 1% of a radius) was missed by up to 13% in tight clusters with the plain single pass. Now 0.0-0.2%. A pair that is already separating gets no second impulse, so a simple two-ball hit is unchanged.
- **S3 expectation corrected.** The plan says the outgoing cushion angle mirrors the incoming angle, but its own sim spec reverses only the normal component and scales it by the restitution, which makes the outgoing angle steeper (tan out = 0.75 tan in). The sim spec is the physics we keep; S3 now checks vy flips and scales by the restitution while vx is unchanged. **Phase 5's reflected assist line must use the same rule, not a mirror image.**
- **S2 uses valid coordinates** (the plan's cue 0.5 / ball 1.0 would put the ball on the cushion): cue (0.25, 0.5), ball (0.5, 0.5) in preset space.
- Public additions to `BilliardsSim` beyond the A11 contract: `Velocity(int)` and `StepsThisShot` (tests and later previews need them).
- `straight_test` needed no power tuning: 0.5 drops ball 1 in TR, and so does anything from 0.3 to 1.0.
- Editor vs. plain .NET: the same 200-shot S5 sequence gave 74 drops in the Unity Editor but 85 in a .NET 8 run of the same code. Both runs pass every check; it is a real example of the Editor/WebGL determinism worry (plan P4), because the chaotic multi-ball shots amplify tiny float differences. Stored solutions must keep passing the verifier in the target runtime.

## Phase 7: authoring tools and content (2026-10-16)

- **7.1 Layout editing, deviation:** instead of a play-mode toggle on `BilliardsApp`, an Editor window, `Tools/OverTimer/Billiards/Table Editor` (`BilliardsTableWindow`). Reasons: it works in edit mode (no play mode, no focus problems), it needs no runtime code in the app, and it runs the same sim and referee. Drag balls (snaps to 0.005 in preset space), right-click removes a ball, add balls by id, order / forbidden / called as text boxes, Load / New.
- **7.2 Record and export:** "Shoot" mode in the same window: pull back anywhere on the felt (with a ghost-ball preview), every quantized shot goes through the real sim and referee and is appended, with ball trails for the last shot. Undo / Clear. **Export refuses unless the recorded shots win the table, and refuses a table the verifier fails**; it writes `Resources/BilliardsPresets/<id>.json` (par = shots used). Solutions can also be recorded against any mirror-free table by loading it: the stored solution is replayed on load.
- **Auto-solver (not in the plan):** `BilliardsSolver` (Editor) brute-forces a solution with the real sim: every aim on a 0.5 degree grid at six powers, keeps shots that make clean progress (legal pot, no foul, no re-spot), ranks them by robustness, searches deeper from the best (iterative deepening, so the first solution has the fewest shots). Option "potting shots must bank". Button in the window. Authoring 8 tables by hand would have taken far longer; the solver also guarantees every shipped table is solvable.
- **`BilliardsPresetJson`:** writes tables with short numbers, one ball per line (`JsonUtility.ToJson` writes `0.45f` as `0.44999998807907107`). `Tools/OverTimer/Billiards/Reformat preset files` rewrites the existing ones.
- **7.3 Robustness, deviation in method:** `BilliardsPresetVerifier.Robustness`. 30 seeded trials per shot, angle jittered +-0.3 degrees and power +-0.02 before quantizing. **Each shot is tested alone**, fired from the exact recorded state, and passes if it does the same thing (same pots in order, same re-spots, same foul flag, same verdict). The plan's literal version (jitter every shot of the solution at once and replay blind) is also reported as "blind replay", but it collapses with solution length (an open-loop replay cannot be right after the first deviation), so it is not used for the knife-edge flag. A table whose WORST shot passes under 70% is flagged knife-edge. Seeded from the table id, so the numbers are repeatable.
- **Validator:** now also rejects balls that overlap at the start and balls that start inside a pocket (needs the physics, so it is given `BilliardsSimParams`).
- **7.4 In-build verify:** cheat menu button "Billiards: verify presets" (same pure-C# verifier, so it works in a build); the button label becomes "Verify: N pass, N fail, N knife-edge, N skipped" and the full per-table report goes to the console. Also new cheat buttons "Billiards table: random / <id>" (`BilliardsDebug.PresetId`, a forced table) for testing and screenshots. **Not yet run in a WebGL development build** (postponed by Ari earlier); it was run in the Editor's play mode: 10 pass, 0 fail, 0 knife-edge.

## Phase 8: card hooks (2026-10-16)

Ari: Han owns the card assets; do a simple hook and adapt Billiards to how each card works. So: **no card assets were created or edited** (nothing under `Resources/CardSO` changed, no art needed from Han yet). What was added is the Billiards side and three effect classes Han can turn into cards.

**How the cards work (read from the code):** an `EffectCardSO` gets `OnPlaced(card)` when it lands on the desk and `OnRemoved(card)` when its effect ends: by itself (`card.EndEffect()`, which flips it face down and registers it in the collection), by a timer (`ScheduleAutoRemove`), by pawning (`CardItem.OnPawned` calls `OnRemoved` if it has not ended) or when the scene is destroyed. "Next X" cards (Overtime/Lucky Ruby, Butterfingers, Insider Tip, Tax Exemption) queue something static and end themselves when the app uses it. Timed cards (cost modifiers, Clock Up / Snail Speed / Time Scarab, Disable App Icon, Robocalls) set a value and put it back in `OnRemoved`.

**New effect classes (new files in `Desk/Items/Cards/CardData`, same pattern as the existing ones):**
- `BilliardsExtraShotCardSO` (Chalk Up, buff): the next round starts with +`extraShots` shots (default 1). Taken at Play, after the bet is really paid. The payout stays the one for the difficulty's normal shots.
- `BilliardsTrickShotCardSO` (Trick Shot, buff): on the next shot, while the pointer is down, faint balls show where every ball ends up (the shot is run on a `Sim.Clone()`, at most every 0.1 s and not again for an unchanged shot; a ball that drops is shown in its pocket). Used up when a shot is fired.
- `BilliardsCueSlipCardSO` (Cue Slip, debuff): the next shot's power is off by up to +-`powerJitter` (0.15), drawn from the seeded `RngService` BEFORE quantizing, so the simulation still gets one exact, replayable input. The result line and the win/lose panel say "Cue slip! power 0.80 became 0.76". Mark the asset as a debuff.

**Contract (`BilliardsPendingEffects`, reworked):** every effect is a grant owned by the card that made it. Using it ends the card (`EndEffect`); if the card goes away first (pawned, timed out, destroyed) its `OnRemoved` calls `Withdraw`, so "pawn the card but keep the effect" is impossible; everything is cleared on every scene load (Restart). Several cards stack: extra shots add up and are taken together at the next round, trick shot and cue slip are used one per shot.

- **9.2 Playtest, what I could and could not do:** I cannot play 20 rounds as people, so `BilliardsBalanceReport` uses a **noisy-hands bot** on the real sim and referee: it follows each table's recorded solution, adapting the planned shot to where the balls really are (it aims at the centre of the widest range of angles that still work, like lining up the ghost ball), and re-plans from the actual state when a shot misses; its aim has a normal error (0.15 / 0.3 / 0.6 degrees) and a power error of 0.03. **It sees the best shot, so its win rate is an upper bound.** Findings (typical hand, 0.3 degrees): the shipped tables are fair; bot win rate Easy 96%, Medium 93%, Hard 63% (at the exact par shots), and per table from 10% (`blocker_01` Hard) to 100%. An aim error multiplies over range (0.6 degrees at 1 unit already moves the object ball 5 degrees), so a patient 1920-build player is about 0.15, a typical one 0.3, a careless one 0.6. The first version of the bot re-planned on a coarse 2-degree grid and played far worse than a person; that was fixed and the check was "zero noise wins 40/40".

- **The bigger finding (section 7 of the report): picking the difficulty after seeing the table.** The racked screen shows the table and the three payouts, the payout depends only on the difficulty, but the win rate varies from 10% to 98% between tables.
